## Contexto

O projeto **Product API** é uma aplicação Spring Boot que gerencia produtos através de operações CRUD básicas.

### Stack atual

| Componente | Versão/Tecnologia |
|------------|-------------------|
| Framework | Spring Boot 3.4.0 |
| Java | 21 |
| Banco de dados | H2 (em memória) |
| Gerenciador | Maven |
| Porta | 8080 |

### Problemas identificados

- Processo manual de build e deploy
- Falta de padronização entre ambientes
- Ausência de testes automatizados no pipeline
- Risco de erros humanos em deploy
- Dificuldade de reprodução do ambiente

### Necessidades

- Automatizar build, testes e deploy
- Garantir consistência entre ambientes
- Facilitar integração contínua
- Preparar base para deploys em nuvem

## Decisão
Implementar um pipeline de CI/CD (Integração e Entrega Contínua) utilizando:


### 1. Containerização com Docker

```dockerfile
FROM maven:3.9.6-eclipse-temurin-21 AS build
FROM eclipse-temurin:21-jre-jammy
COPY --from=build /app/target/*.jar app.jar
ENTRYPOINT ["java", "-jar", "app.jar"]
```

### 2. Pipeline GitHub Actions

```yml 
jobs:
  build-and-test:  # Build e testes
  docker-build:    # Criação da imagem Docker
  deploy-homolog:  # Deploy em homologação
```


## 3. Estrutura do Pipeline

| Fase | Ação | Ferramenta |
|------|------|-------------|
| Trigger | Push nas branches main/master | GitHub Events |
| Build | Compilação e empacotamento | Maven |
| Testes | Execução de testes unitários | JUnit + JaCoCo |
| Container | Criação da imagem Docker | Docker CLI |
| Deploy | Publicação em ambiente de homologação | Scripts customizados |


## Alternativas Consideradas

| Alternativa | Prós | Contras |
|-------------|------|---------|
| **Jenkins** | Mais customizável | Requer servidor próprio, overhead operacional, sem integração nativa com GitHub |
| **GitLab CI** | Bom para projetos GitLab | Projeto está no GitHub, exigiria migração |
| **Deploy manual** | Simples inicialmente | Alto risco de erro humano, sem rastreabilidade, difícil rollback |
| **Apenas Docker** | Ambientes consistentes | Build manual, sem automação de testes |



## Consequências

### Positivas

- Automação total do build e deploy
- Consistência entre ambientes via Docker
- Gatilhos automáticos a cada push
- Histórico rastreável via GitHub Actions
- Base preparada para nuvem (AWS, Azure, GCP)
- Testes executados automaticamente antes do deploy

### Negativas

- Tempo adicional de configuração inicial
- Complexidade do pipeline (3 jobs encadeados)
- Dependência externa do GitHub Actions
- Gerenciamento de secrets (Docker Hub credentials)


## Riscos e Mitigações

| Risco | Probabilidade | Mitigação |
|-------|---------------|------------|
| Falha no build do Docker | Média | Cache de camadas Docker |
| Pipeline quebrar em PRs | Baixa | Testes em pull requests separados |
| Credenciais expostas | Baixa | Uso de Secrets do GitHub |
| Build muito lento | Média | Cache do Maven implementado |


## Justificativa

A decisão foi baseada nos seguintes critérios:

| Critério | Motivo |
|----------|--------|
| Integração nativa | GitHub Actions já integrado ao repositório |
| Custo zero | GitHub Actions oferece minutos gratuitos |
| Simplicidade | YAML declarativo e fácil de entender |
| Escalabilidade | Pipeline preparado para adicionar mais estágios |
| Padrão de mercado | Docker + GitHub Actions é amplamente adotado |



## Comparativo de Custo-Benefício

| Critério | Manual | Pipeline + Docker |
|----------|--------|-------------------|
| Tempo de setup | 5 min | 30 min (único) |
| Tempo de deploy | 5 min | 1 min (automático) |
| Erro humano | Alto | Zero |
| Consistência | Baixa | Alta |
| Rastreabilidade | Nenhuma | Total |

## Jobs do Pipeline

| Job | Dependência | Executa em | Descrição |
|-----|-------------|------------|------------|
| `build-and-test` | Nenhuma | Ubuntu Latest | Compila código e executa testes |
| `docker-build` | `build-and-test` | Ubuntu Latest | Cria imagem Docker |
| `deploy-homolog` | `docker-build` | Ubuntu Latest | Deploy em homologação (apenas `master`) |
